# Local Wi-Fi gateway setup preview

The setup screen uses the supported CoreWLAN client to discover an active station interface and SSID, and `getifaddrs` to find the interface's assigned IPv4. It accepts RFC1918 addresses only. It never scans nearby networks, asks for a manual SSID/IP, changes router settings, or configures USB.

If CoreWLAN withholds the SSID and Core Location reports authorization as not determined, the screen explains why and exposes a button that calls the documented macOS location authorization API. The app bundle declares `NSLocationUsageDescription`. It requests only while-in-use permission; it does not request Always access or GPS coordinates. If the user denies permission, macOS restricts it, or CoreWLAN still returns no SSID, the setup stays blocked and does not use a manually typed fallback. The user must grant Location Services in System Settings if macOS denied a prior request.

The owner must explicitly opt in to the exact currently detected SSID. The screen then produces an in-memory XML plist preview for a per-user job at `~/Library/LaunchAgents/com.thozha.companion-wifi-gateway.plist`, with mode 0600 and only the gateway enable flag, SSID/interface/private-IP/port/hostname, interpreter paths and PATH. It contains no API key, device token, pairing secret, database path or private key. The disable preview targets only this job and plist and states that pairing, task history, TLS identity and logs are retained.

The UI requires a separately confirmed action after the complete plist preview. The manager writes the plist owner-only, then bootstraps only the per-user Thozha job. Disable first boots out that job and only then removes its plist; it leaves pairing/task data, TLS identity and logs untouched. The app refuses to enable the login-time job unless it is installed at `/Applications/Thozha Setup.app`, so the LaunchAgent does not reference a movable development bundle. The LaunchAgent does not use KeepAlive, avoiding restart loops when the SSID changes; after a network change stops the gateway, the owner can reopen setup and enable it again.

The gateway Python runner spawns its TLS proxy and DNS-SD advertiser in detached sessions and cleans them up in its `finally` block. The app bundle includes a small supervisor executable that translates launchd's SIGTERM into SIGINT for the Python runner and waits for cleanup before exiting. Without this wrapper, bootout may leave the detached child processes behind.

Tests use fake snapshots, file operations and launchctl operations. They verify opt-in, owner-only plist mode, exact safe environment keys, rollback on failed bootstrap, bootout/removal scope, and no side effects before confirmation. Tests make no TCC request, real filesystem write, process launch or `launchctl` call. In this coding session the real UI was not launched, the Location Services prompt was not requested, and no LaunchAgent/gateway service was installed or started.

macOS permission references: [Core Location authorization](https://developer.apple.com/documentation/corelocation/requesting-authorization-to-use-location-services), [CoreWLAN](https://developer.apple.com/documentation/CoreWLAN), [CoreWLAN `ssid()`](https://developer.apple.com/documentation/corewlan/cwinterface/ssid%28%29).
