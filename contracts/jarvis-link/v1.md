# Jarvis Link Wire Protocol v1

Status: prototype contract; no production deployment.

## Identities and algorithms

- Each device has an ECDSA P-256 signing key and a separate P-256 ECDH encryption key. Private keys stay on that device. Relay registration stores only SPKI public keys and revocation state.
- Signed requests use ECDSA P-256 with SHA-256. Signatures are DER-encoded and Base64URL-encoded without padding.
- Each message is encrypted with AES-256-GCM. The sender makes a fresh ephemeral P-256 ECDH key per message, derives a 256-bit key with HKDF-SHA-256, and uses a fresh 96-bit GCM IV.
- HKDF salt is the 16-byte message ID. HKDF info is UTF-8 `JarvisLink/v1\n<tenant_id>\n<from_device_id>\n<to_device_id>`. GCM AAD is the canonical header described below.
- Public keys are DER SubjectPublicKeyInfo, Base64URL without padding. IDs are UUIDv4 lowercase hex without hyphens. Nonces are 32 random bytes, Base64URL without padding.
- Relay authentication is per-request signed proof; there are no shared bearer secrets in the Worker or Durable Object.
- Signing and ECDH keys are bound together by a host-root-signed DeviceCertificate. Clients only encrypt to an ECDH key after validating that certificate against the pinned tenant host-root key. Device names reject CR/LF, C0 controls, and DEL; free text never enters newline-delimited signed bytes.

## Canonicalization

All signed bytes use the following ASCII line format with LF separators, no trailing LF, and no user-controlled free text in these fields. Identifiers, enum values, timestamps, URL-safe base64, and hex values have constrained grammars.

Request signing string:

`JARVIS-LINK-REQUEST-V1\n<tenant_id>\n<device_id>\n<timestamp_unix_ms>\n<nonce_b64url>\n<HTTP_METHOD_UPPER>\n<path_and_query>\n<body_sha256_hex>`

Envelope signing string (`ciphertext_sha256_hex` is SHA-256 over decoded encrypted bytes, including the GCM tag, not the Base64URL text):

`JARVIS-LINK-ENVELOPE-V1\n<tenant_id>\n<message_id>\n<from_device_id>\n<to_device_id>\n<to_key_id>\n<kind>\n<issued_at_unix_ms>\n<expires_at_unix_ms>\n<ephemeral_pubkey_b64url>\n<iv_b64url>\n<ciphertext_sha256_hex>`

Header/AAD bytes are the envelope signing string excluding the final ciphertext digest. The encrypted payload is UTF-8 JSON but is opaque to the relay.

## Enrollment and DeviceCertificate

A tenant has a pinned host-root P-256 signing public key. The host keeps the matching private key; the relay never receives it. The initial host root is pinned out-of-band during trusted local setup. In this prototype, host bootstrap is a local test/admin operation and never uses a Mac execution credential.

A DeviceCertificate has exactly these fields:

```json
{
  "v": 1,
  "tenant_id": "…",
  "device_id": "32-lowercase-hex",
  "device_role": "host|companion",
  "signing_public_key_b64url": "…",
  "encryption_public_key_b64url": "…",
  "not_before_unix_ms": 0,
  "expires_at_unix_ms": 0,
  "certificate_id": "…",
  "issuer_device_id": "32-lowercase-hex",
  "signature_b64url": "…"
}
```

`device_id` is the first 16 bytes of SHA-256(signing SPKI DER), lowercase hex. `certificate_id` is a random 16-byte value encoded as 32 lowercase hex. The host-root signature is ECDSA P-256/SHA-256, DER signature bytes, Base64URL without padding. The exact signed bytes are ASCII/UTF-8, LF-delimited, no trailing LF:

`JARVIS-LINK-DEVICE-CERT-V1\n<v>\n<tenant_id>\n<device_id>\n<device_role>\n<signing_public_key_b64url>\n<encryption_public_key_b64url>\n<not_before_unix_ms>\n<expires_at_unix_ms>\n<certificate_id>\n<issuer_device_id>`

The host-root public key is pinned out-of-band during trusted local setup. The host keeps the matching private key; the relay never receives it. In this prototype, host bootstrap is a local test/admin operation and never uses a Mac execution credential. Device names must be 1–64 UTF-8 bytes and reject CR/LF, C0 controls, and DEL; free text never enters newline-delimited signed bytes.

The host creates one-use enrollment invitations; the relay stores only SHA-256(secret), tenant, role, and expiry. A new device proves possession of its signing key to a challenge. This produces `PENDING_HOST_CERTIFICATION` only. The host retrieves the pending public keys, obtains the user's local approval, signs a DeviceCertificate, and submits it to the relay. The relay compares all certificate keys/fields to the pending record and validates the signature against the pinned tenant root before activating the device. A companion verifies the sender certificate before accepting a message. A sender fetches and verifies the recipient certificate, then checks `to_key_id == certificate_id` before ECDH encryption; relay-provided encryption keys are never trusted without this signed certificate.

`GET /v1/devices/{device_id}/certificate` returns the active signed DeviceCertificate. Inbox responses include the encrypted envelope plus the sender's signed DeviceCertificate; they do not include a trusted key alone. Clients must reject a certificate with a wrong root signature, wrong tenant/device ID, wrong key ID, wrong role, or expired lifetime. Revocation is immediate and prevents future signed requests and message delivery.

## Messages

Envelope JSON fields:

```json
{
  "v": 1,
  "tenant_id": "tenant-id",
  "message_id": "32-lowercase-hex",
  "from_device_id": "32-lowercase-hex",
  "to_device_id": "32-lowercase-hex",
  "to_key_id": "recipient-device-certificate-id",
  "kind": "task.submit|task.progress|task.result|approval.request|approval.decision|task.cancel",
  "issued_at_unix_ms": 0,
  "expires_at_unix_ms": 0,
  "ephemeral_pubkey_b64url": "...",
  "iv_b64url": "...",
  "ciphertext_b64url": "...",
  "sender_signature_b64url": "..."
}
```

`to_key_id` equals the `certificate_id` in the host-root-verified recipient DeviceCertificate. The sender derives it from that certificate; the DO compares it to the active certified recipient record and rejects mismatch. The signature covers the envelope signing string. The receiver verifies the sender DeviceCertificate against its pinned host root, sender identity, expiry, duplicate message ID, envelope signature, AES-GCM tag, and message-specific schema before acting. The relay stores only the encrypted envelope, signed public certificates, and delivery state.

`task.submit` payload is exactly `{"objective": <1–4096 chars>, "capability_scope": [<unique values from `read_only`, `web_research`, `desktop_observation`>]}`; any other field (and any key named `command`, `cmd`, `shell`, `shell_command`, `script`, `executable`, `exec` at any depth) is rejected. It carries an objective plus an exact capability scope; it never carries shell text or arbitrary executable instructions. A host adapter maps accepted objectives into the supervisor task API. Consequential steps pause and create the existing exact-operation approval record. `approval.request` includes task ID, operation, target, canonical-argument digest, expiry, and a human-readable redacted summary, encrypted end-to-end. `approval.decision` contains only task ID, approval ID, decision, digest, and idempotency nonce. The host/supervisor revalidates exact arguments before dispatch.

## Relay delivery invariants

- All API/WebSocket actions require a device signature and nonce. Nonces and message IDs are unique within the tenant and retained through expiry plus replay window.
- Every message has an expiry capped at 24 hours. Expired messages cannot be claimed or delivered.
- Delivery transitions are atomic: `QUEUED -> DELIVERED -> ACKED`; retrying a delivery never executes a message twice.
- A receiver ACK includes a signed `message_id`, status, and result digest. The sender may safely retry the same request with the same idempotency key.
- Revoked devices cannot poll, connect, submit, or receive. Queue entries addressed to a revoked device are marked undeliverable and expire.
- Task result and progress payloads are encrypted to the intended recipient. The relay cannot decrypt or synthesize approval decisions.

## HTTP API contract

All IDs below use the 32-character lowercase hex form. JSON bodies are UTF-8, at most 64 KiB unless a route states a smaller limit. Timestamps are Unix milliseconds.

### Signed request authentication

All enrolled-device routes require these headers:

- `X-Jarvis-Link-Device`: sender device ID.
- `X-Jarvis-Link-Tenant`: tenant ID; included in the signed request string to prevent cross-tenant replay.
- `X-Jarvis-Link-Timestamp`: Unix milliseconds; maximum clock skew 60 seconds.
- `X-Jarvis-Link-Nonce`: 32 random bytes, Base64URL without padding.
- `X-Jarvis-Link-Signature`: ECDSA P-256/SHA-256 signature over the request signing string from this spec, Base64URL without padding.

The Worker resolves the device only inside its tenant Durable Object, checks that it is active and not revoked, enforces timestamp, atomically consumes the nonce, then routes the operation. The body digest is SHA-256 of the exact transmitted body bytes. Do not reserialize JSON after signing.

### Enrollment

`POST /v1/enrollment/invitations` — host-signed. Returns a one-use, random invitation secret; relay stores only its SHA-256 hash.

Request:

```json
{"tenant_id":"…","device_role":"companion","expires_in_seconds":600}
```

Response (secret is returned once; relay stores only its SHA-256 hash):

```json
{"invitation_id":"…","invitation_secret_b64url":"…","expires_at_unix_ms":0}
```

`POST /v1/enrollment/challenge` — unauthenticated but requires the one-use invitation secret.

Request:

```json
{"invitation_id":"…","invitation_secret_b64url":"…","device_name":"…","device_role":"companion","signing_public_key_b64url":"…","encryption_public_key_b64url":"…","client_nonce_b64url":"…"}
```

Response:

```json
{"challenge_id":"…","challenge_b64url":"…","device_id":"…","expires_at_unix_ms":0}
```

The returned challenge is 32 random bytes. `device_id` is derived from the signing public key. The recipient signs UTF-8 `JARVIS-LINK-ENROLL-V1\n<tenant_id>\n<invitation_id>\n<challenge_id>\n<device_id>\n<device_name_b64url>\n<device_role>\n<signing_public_key_b64url>\n<encryption_public_key_b64url>\n<client_nonce_b64url>\n<challenge_b64url>`. Device names are Base64URL-encoded UTF-8 before signing.

`POST /v1/enrollment/complete` — unauthenticated, signed by the new device key.

Request:

```json
{"invitation_id":"…","challenge_id":"…","device_name":"…","device_role":"companion","signing_public_key_b64url":"…","encryption_public_key_b64url":"…","client_nonce_b64url":"…","challenge_b64url":"…","signature_b64url":"…"}
```

Response: `{"device_id":"…","tenant_id":"…","status":"PENDING_HOST_CERTIFICATION"}`. Completion atomically consumes the challenge/invitation but grants no access. Retries with the same invitation are rejected as replay. The host then retrieves pending enrollment, asks for local confirmation, signs a DeviceCertificate, and calls `POST /v1/enrollment/certify`; the relay verifies the host-root signature and exact key/tenant/role match before activation.

`GET /v1/devices/{device_id}/certificate` returns `{ "certificate": <DeviceCertificate> }` for an active device in the caller's tenant. `GET /v1/enrollment/pending` returns `{"enrollments":[...]}` with candidate identity/key fields only to a signed host. `POST /v1/enrollment/certify` — signed by an active host and carrying `{ "certificate": <DeviceCertificate> }`; response is `{"device_id":"…","status":"active"}`. The host must sign locally only after user approval.

`POST /v1/devices/{device_id}/revoke` — signed by an active host. Body `{"reason_code":"owner_revoked"}`. Response `{"device_id":"…","status":"revoked"}`. Revocation is idempotent and invalidates polling, WebSocket, submit, and ACK operations immediately.

### Message delivery

`POST /v1/messages` — signed by an active device; body is one protocol-v1 encrypted envelope. Response `{"message_id":"…","status":"queued","expires_at_unix_ms":0}`. Repeating the same `message_id` returns the original queued/delivery state but never creates a second operation. Reusing the ID with different envelope bytes returns 409.

`GET /v1/devices/{device_id}/inbox?limit=20` — recipient-signed (v1 returns `next_cursor:null`; clients poll/ACK the bounded page before requesting more). Response `{"messages":[{"envelope":<envelope>,"sender_certificate":<DeviceCertificate>},…],"next_cursor":"…|null"}`. Only messages addressed to the caller are returned. Delivery is at-least-once until an ACK; the host/companion deduplicates by `message_id` before processing.

`POST /v1/messages/{message_id}/ack` — recipient-signed. Body `{"status":"received|rejected","result_digest":"<64 hex or empty>"}`. Response `{"message_id":"…","status":"acked"}`. Repeated identical ACK is idempotent; conflicting ACK is rejected.

`GET /v1/devices/{device_id}/stream` — optional WebSocket. The HTTP upgrade itself carries signed request headers. After upgrade, the DO sends only a non-sensitive `message_available` hint; the client retrieves the ciphertext through the signed inbox endpoint and ACKs over signed HTTP. Use the Durable Object Hibernation WebSocket API. WebSocket messages never carry plaintext task or approval content.

### Stable error shape

Errors are JSON: `{"error":{"code":"…","message":"…","request_id":"…"}}`. The Worker never echoes signatures, invitation secrets, bearer/bootstrap material, plaintext payloads, or tool arguments in error bodies or logs. Expected codes include `UNAUTHORIZED`, `DEVICE_REVOKED`, `NONCE_REPLAY`, `MESSAGE_REPLAY`, `MESSAGE_EXPIRED`, `INVALID_SIGNATURE`, `INVALID_ENVELOPE`, `NOT_RECIPIENT`, `RATE_LIMITED`, and `NOT_FOUND`.
# Thozha Live voice stream v2 (USB development transport)

This protocol is a separate realtime audio lane. It is not sent through Telegram.
The current development server binds only to `127.0.0.1:8766` and is reachable
from Android only through the explicitly installed USB ADB reverse mapping. The
server requires an existing paired-device bearer token and validates it against
the supervisor's paired-device table through a read-only SQLite connection.
It refuses non-loopback peers and non-loopback bind addresses. No Mac control
tools are exposed by the voice lane.

## Handshake and control

The phone connects to `ws://127.0.0.1:8766/v1/voice/session` with the existing
paired token in the `Authorization: Bearer` handshake header. Tokens must never
appear in query strings, logs, transcript events, or audio frames.

The first text message is `{"type":"start","protocol":2,"session_id":"<uuid>",
"device_id":"<paired id>","sample_rate":16000,"channels":1}`. Server replies
`session_ready`. Controls include `end_turn` with input turn ID and next input
sequence, `respond`/`local_speech`/`local_complete` bound to that same input turn,
`interrupt`, and
`end_session`. The server issues `transcript`, `response_text`, lifecycle,
error, and completion events. The Mac prompt is text-only; no tool schemas are
passed to the model. Transcribed conversational turns use the existing direct
OpenJarvis WebSocket stream, with `transient=true` so transcript/result text is
not written to the trace database. Explicit Mac actions are separately routed
through the phone's supervisor-backed task submission path.

## Binary audio frame

WebSocket binary payloads use the same 24-byte big-endian header on both
directions: magic `THZV` (4 bytes), version `u8` (=2), kind `u8` (1=phone PCM,
2=Mac PCM), sample rate `u16`, turn ID `u32`, sequence `u32`, monotonic
capture/emit time `u64`, then signed 16-bit little-endian mono PCM. Phone input
is 16 kHz. Mac TTS output may be 24 kHz. Frame sequences start at zero per turn;
turn IDs distinguish interrupted/stale PCM from a later response. Payloads
are bounded to 64 KiB each and 20 seconds per input turn. Duplicate, skipped,
invalid-rate, malformed, or over-limit frames close/reject the current session.

## Deployment boundary

The v1 audio socket is intentionally loopback-only and has no TLS because its
only supported path is the authenticated USB reverse tunnel. It must not be
bound to Wi-Fi, Ethernet, a VPN, a public interface, or exposed with a proxy.
An authorized private-LAN transport requires a separate TLS-pinned deployment
and pairing review; this protocol document does not grant that authorization.
