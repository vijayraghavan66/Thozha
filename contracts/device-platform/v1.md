# Device platform Web contract v1 — proposed, not a deployed API

The executable response schema is `web/src/api/devicePlatform.ts` (`devicePlatformInventory`). This is an additive owner-scoped reporting API, not a new backend, identity store, transport, task service, or permission authority. Current Beta 1 does **not** implement this route. UI fixtures are Playwright-only.

## Existing production-compatible APIs reused unchanged

- `GET /v1/web/devices` → `{devices: WebDevice[], count}`; only active, explicitly owner-mapped companion identities. `WebDevice` contains `device_id`, `device_name`, `created_at`, `expires_at`, `status: "active"`. Active means credential validity, not network presence.
- `GET /v1/web/devices/{id}` and `POST /v1/web/devices/{id}/revoke` with `{confirm:true}`. Revocation invalidates companion access and cleans notification registration; no history deletion API exists.
- `POST /v1/web/devices/pairing-invitations` with `{transport:"wifi"}`; signed v2 invitation and `qr_payload` from existing server. The browser does not sign or alter the payload.
- `GET /v1/web/devices/pairing-invitations/{id}`, `POST .../{id}/cancel` with `{}`.
- `GET /v1/web/devices/pairing-requests?limit=50`, `POST /v1/web/devices/pairing-requests/{id}/decision` with `{decision:"approve"|"reject"}`.
- States: `INVITED → PENDING_CONFIRMATION → APPROVED → TOKEN_ISSUED`; terminal alternatives `REJECTED`, `EXPIRED`, `CANCELLED`. Approval is **not** token claim or Web-owner mapping. Existing Android key-proof claim stays outside browser.
- Existing `/v1/web/tasks`, task events/SSE, `/v1/web/approvals` and digest-bound idempotent decisions remain authoritative. `requester_device_id` is a requester identity, **not** proof of execution destination.

All use the existing same-origin HttpOnly session, CSRF on mutations, no-store responses, existing trusted-Origin and owner checks. Never accept a companion bearer, permanent API key, local-only admin bypass, arbitrary upstream, or browser-supplied owner ID.

## Proposed inventory endpoint

`GET /v1/web/device-platform/inventory` returns HTTP 200 `application/json`, `Cache-Control: no-store`:

```json
{
  "contract_version": 1,
  "observed_at": "2026-11-25T12:00:00Z",
  "stale_after_seconds": 30,
  "devices": [],
  "agents": []
}
```

- `observed_at`: UTC/offset ISO timestamp generated by host, not the browser.
- `stale_after_seconds`: integer 1–300. UI downgrades stale/future-skewed observations to unknown, and polls every 15 seconds only in foreground while connected. Network failure never becomes an empty inventory.
- `devices`: at most 1000 unique owner-mapped records: `{device_id, platform, os_version, app_version, presence, capabilities}`. Device IDs are existing lowercase 32-hex supervisor IDs. OS/app versions are nullable strings (max 100). No device-name/platform guessing.
- `agents`: at most 1000 unique records: `{agent_id, device_id, name, runtime, platform, version, lifecycle, presence, capabilities}`. `agent_id`: stable 32-hex runtime identifier resolved by the existing host; `device_id`: existing paired identity or null for host execution. `name` max 120, `runtime` max 100, `version` nullable max 100.
- `platform`: `macos | android | windows | linux | ios | unknown`.
- `lifecycle`: `enrolling | active | suspended | revoked | incompatible`.
- `presence`: `{state:"online"|"offline"|"unknown", last_seen_at: ISO timestamp|null}`. The server must derive presence from authenticated heartbeats, not credential validity or discovery advertisements. Last-seen is observational, not task authorization.
- `capabilities`: at most 200 `{id: string(1..100), label: string(1..120), supported:boolean, authorization:"allowed"|"approval_required"|"denied"|"unknown"}`. Empty means not reported, not unrestricted access. Authorization is informational; supervisor gates always apply.
- 401 expires browser session; 403 rejects access; 404/501 indicate unsupported contract (no fabricated inventory, no repeated polling); 409 incompatible version; 503 transient reporting failure. Never fall back to legacy administrative or device-token routes.

No raw certificates, token material, QR challenges, local filesystem paths or secrets belong in inventory. Server must filter all records by existing authenticated Web principal and existing enrollment/mapping authority before serialization, including nested capabilities.

## Future enrollment/lifecycle proposal — not invoked by this UI

Implement on the existing supervisor identity authority only after review:

- `POST /v1/web/device-platform/enrollments` with CSRF, Idempotency-Key and `{contract_version:1, platform:"macos"|"windows"|"linux"|"ios", role:"execution_agent"|"companion"}` → 201 `{contract_version:1,enrollment_id,expires_at,status:"pending",invitation}`. `invitation` must follow a separately reviewed signed host-bound protocol; do not reuse the Web session as an agent credential. Maximum TTL 5 minutes, one use, no bearer in URLs/logs/localStorage.
- `GET /v1/web/device-platform/enrollments/{id}` → 200 `{contract_version:1,enrollment_id,expires_at,status:"pending"|"awaiting_owner"|"approved"|"claimed"|"rejected"|"expired"|"cancelled",agent_id:null|id}`. Owner approval and device key proof are distinct gates.
- `POST .../enrollments/{id}/decision` with CSRF, Idempotency-Key, `{decision:"approve"|"reject",expected_device_fingerprint}` → 200 same status response. Wrong identity/state → 409; expired → 410. Approved != claimed. Do not expose claim secrets to the Web owner.
- `POST /v1/web/device-platform/agents/{id}/lifecycle` with CSRF, Idempotency-Key, `{action:"suspend"|"resume"|"revoke",expected_version:string,confirm:true}` → 200 `{contract_version:1,agent_id,lifecycle,version}`. Supervisor must revoke credentials and revalidate queued work without replay on resume; preserve historical task references. No lifecycle mutation is currently advertised as working.
- Windows/Linux require signed artifacts, verified immutable download URLs, digest, architecture/minimum-OS/protocol compatibility, release provenance and uninstall/update policy before a Download button may appear. No such artifact has been verified here.
- Android stays on existing Kotlin v2 QR pairing. iOS must use a native companion with explicit foreground/user-mediated capabilities; no unrestricted background daemon, arbitrary cross-app execution, or Android permission parity.

## Task routing boundary

Do not overload `requester_device_id`. A future reviewed task contract needs server-resolved `target_agent_id`/`target_device_id`, required capability IDs, an immutable authorization snapshot/version, server compatibility validation, and the same target bound into operation digests and approval display. Reject disconnected/incompatible/unauthorized targets server-side. Preserve existing task IDs, event stream and idempotency namespace; do not create a parallel history. Until these exist, the UI links to the existing task composer and labels requester context accurately; there is no fabricated target picker.
